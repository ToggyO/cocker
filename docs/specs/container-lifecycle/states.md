## Назначение

Этот документ определяет состояния контейнера, допустимые переходы между ними и требования к поведению runtime при успешных и ошибочных операциях.

Состояние контейнера описывает состояние управления контейнером в `cocker`. Оно не обязано полностью совпадать с состоянием Linux-процесса в каждый момент времени.

## Термины

### Контейнер

Управляемый `cocker` набор из процесса, Linux isolation resources, resource limits, root filesystem и metadata.

### Runtime resource

Ресурс, созданный для работы контейнера: процесс, namespace, mount, cgroup, pipe или временный файл.

### Cleanup

Упорядоченное освобождение runtime resources и сохранение результата операции.

### Terminal state

Состояние, из которого контейнер не переходит в новое рабочее состояние. В MVP это `stopped` и `failed`.

## Состояния

### `created`

Metadata контейнера создана, но основной процесс ещё не запущен.

В этом состоянии допускается:

- запуск;
- удаление незапущенного контейнера, если такая команда будет добавлена;
- просмотр metadata.

### `starting`

Runtime выполняет подготовку процесса и ресурсов: namespaces, rootfs, mounts, cgroup и stdio.

Пользователь не должен считать контейнер работающим, пока переход в `running` не завершён.

Ошибка на этом этапе переводит контейнер в `failed` после выполнения доступного cleanup.

### `running`

Основной процесс успешно запущен и считается работающим.

В этом состоянии допускается:

- просмотр состояния;
- отправка сигнала остановки;
- ожидание естественного завершения процесса.

### `stopping`

Runtime инициировал остановку контейнера и ждёт завершения процесса или истечения timeout.

Повторная команда `stop` должна быть идемпотентной или возвращать понятный результат о том, что остановка уже выполняется.

### `stopped`

Основной процесс завершён, exit status сохранён, а созданные runtime resources очищены.

Это нормальное конечное состояние независимо от того, завершился процесс с exit code `0`, ненулевым кодом или сигналом.

### `failed`

Операция запуска или управления завершилась ошибкой, из-за которой контейнер не может продолжить обычный lifecycle.

Перед переходом в это состояние runtime должен выполнить best-effort cleanup и сохранить диагностическую ошибку.

## Допустимые переходы

```text
created  -> starting
starting -> running
starting -> failed
running  -> stopping
running  -> stopped
running  -> failed
stopping -> stopped
stopping -> failed
```

Нельзя напрямую переходить:

- `created -> running`;
- `created -> stopped`;
- `stopped -> running`;
- `failed -> running`.

Повторный запуск остановленного контейнера в MVP не поддерживается. Позже это может быть отдельным решением, поскольку повторный запуск может требовать создания новых namespaces, mounts и cgroup.

## Основной сценарий запуска

```text
created
   │ run
   ▼
starting
   │ resources prepared and process started
   ▼
running
   │ process exits
   ▼
stopped
```

Требования:

1. Metadata создаётся до начала потенциально долгих runtime operations.
2. Переходы состояния сохраняются последовательно.
3. В `running` контейнер переводится только после успешного запуска основного процесса.
4. После завершения процесса runtime сохраняет exit status.
5. Cleanup выполняется до фиксации окончательного состояния `stopped`.

## Сценарий ошибки запуска

```text
created -> starting -> failed
```

Ошибкой запуска считаются, например:

- недоступный rootfs;
- невозможность создать namespace;
- ошибка mount operation;
- невозможность создать или настроить cgroup;
- невозможность запустить команду;
- отказ подключения stdio.

В metadata должны быть сохранены:

- этап, на котором произошла ошибка;
- человекочитаемое описание;
- исходная причина, если её можно безопасно представить пользователю;
- результат cleanup.

## Сценарий остановки

```text
running -> stopping -> stopped
```

Минимальное поведение:

1. Найти PID основного процесса по metadata.
2. Отправить SIGTERM.
3. Ждать завершения до заданного timeout.
4. Если процесс не завершился, отправить SIGKILL.
5. Дождаться завершения процесса.
6. Выполнить cleanup.
7. Сохранить exit status и причину остановки.

Если отправка сигнала невозможна или cleanup завершился существенной ошибкой, состояние должно отражать `failed`, а диагностика должна содержать все выполненные шаги.

## Идемпотентность

Повторное чтение состояния не должно менять систему.

Повторный `stop` для `stopped` должен завершаться предсказуемо и не пытаться отправить сигнал несуществующему процессу.

Cleanup должен быть безопасен при повторном вызове. Например, удаление уже отсутствующего временного каталога не должно превращать успешный cleanup в необъяснимую ошибку.

## Согласованность состояния

Состояние в metadata и фактическое состояние Linux могут временно расходиться во время аварии процесса или хоста. При следующем обращении `cocker` должен уметь обнаружить очевидные признаки stale state, например отсутствующий PID, и пометить запись диагностически.

Полное восстановление после падения daemon не входит в первую реализацию и будет отдельным архитектурным вопросом.

## Exit status

Для завершившегося контейнера нужно хранить:

- exit code, если процесс завершился обычным способом;
- signal number, если процесс был завершён сигналом;
- причину остановки, если остановку инициировал `cocker`;
- время завершения.

CLI должен возвращать пользователю результат запуска в соответствии со спецификацией команды `run`. Точное отображение signal termination и диапазона CLI exit codes будет определено в спецификации CLI.

## Наблюдаемость

Каждый переход должен иметь:

- timestamp;
- предыдущий статус;
- новый статус;
- причину перехода;
- correlation/container ID.

В MVP достаточно сохранять эти данные в metadata и писать диагностические сообщения в stderr или runtime log. Полноценная event stream модель появится позже.

## Критерии приёмки

- Все состояния и переходы из этого документа представлены в domain model.
- Недопустимый переход приводит к понятной ошибке.
- Ошибка запуска приводит к cleanup и состоянию `failed`.
- Нормальное завершение приводит к cleanup и состоянию `stopped`.
- `stop` использует timeout и эскалацию SIGTERM -> SIGKILL.
- Повторный `stop` не создаёт новый процесс и не ломает metadata.
- Для завершённого контейнера доступен exit status.
- Unit tests проверяют таблицу переходов.
- Linux integration tests проверяют основной lifecycle с реальным процессом.
