# Ревью готовой фичи

## Назначение

Этот документ задаёт порядок финального review для завершённой change или feature.
Он применяется после выполнения всех задач из `tasks.md` и до перехода к следующему блоку.

Review проверяет не только стиль кода. Цель — убедиться, что изменение соответствует спецификации, сохраняет архитектурные границы, имеет проверяемое поведение и улучшает состояние проекта.

## Источники критериев

При ревью используются следующие руководства:

- [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) — идиомы, имена, ошибки, комментарии, структура пакетов и тесты;
- [Effective Go](https://go.dev/doc/effective_go) — базовые принципы читаемого Go-кода. Документ содержит старые разделы и не покрывает современные возможности языка, поэтому он не заменяет актуальную документацию;
- [Go Doc Comments](https://go.dev/doc/comment) — правила документирования экспортируемых API;
- [Google Code Review: The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html) — критерии полезности изменения, приоритет фактов над личными предпочтениями и разделение обязательных замечаний от рекомендаций.

Эти руководства адаптируются к архитектуре `cocker`, его Linux-only ограничениям и учебной цели проекта.

## Уровни замечаний

Каждое замечание получает уровень:

- **Blocker** — код не собирается, тесты не проходят, нарушена спецификация, есть ошибка lifecycle, cleanup, безопасности или потеря данных. Без исправления feature не принимается;
- **Major** — существенная ошибка поведения, архитектуры, обработки ошибок или тестового покрытия. Исправление обязательно до завершения feature;
- **Minor** — локальное улучшение читаемости или поддерживаемости, которое желательно исправить в текущей change;
- **Nit** — необязательное замечание по стилю или формулировке. Оно не блокирует принятие;
- **Question** — вопрос для понимания решения. Сам по себе не является дефектом.

Уровень должен объяснять практическое последствие замечания. Личные предпочтения без технического обоснования не превращаются в обязательные требования.

## Порядок review

### 1. Зафиксировать границы

Перед чтением кода проверить:

- какая change и какой блок рассматриваются;
- какие задачи входят в review;
- какие изменения явно исключены;
- какая спецификация, ADR и архитектурные документы являются источниками требований.

Если фактический scope шире согласованного, это отдельное замечание до анализа деталей реализации.

### 2. Проверить результат сборки и автоматические проверки

Нужно выполнить подходящие для текущей change команды:

```text
gofmt -w <изменённые Go-файлы>
go test ./...
go vet ./...
go build ./cmd/cocker
```

Дополнительно выполняются `go test -race ./...`, integration tests и privileged checks, если они относятся к изменению.

В отчёте фиксируются команды, результаты и проверки, которые невозможно было выполнить.

### 3. Сверить поведение со спецификацией

Для каждого acceptance criterion нужно установить одно из состояний:

- выполнен и подтверждён тестом;
- выполнен и подтверждён ручной проверкой;
- не выполнен;
- не проверен из-за ограничения окружения.

Нельзя считать feature готовой только потому, что компиляция и unit tests успешны.

### 4. Проверить архитектуру и зависимости

Проверяются:

- соответствие структуры пакетов package structure и design-документам;
- направление зависимостей между CLI, runtime и platform слоями;
- отсутствие platform-specific деталей в platform-neutral API;
- отсутствие преждевременных абстракций и дублирования;
- отсутствие случайного расширения scope;
- соответствие новых решений существующим ADR.

Для Linux-кода отдельно проверяется, что platform assumptions видны в имени файла, build tags, тестах или документации.

### 5. Проверить корректность реализации

Обязательные вопросы:

- правильно ли обрабатываются normal path и все ожидаемые error paths;
- сохраняются ли причины ошибок через wrapping и `errors.Is`/`errors.As`;
- не теряются ли ошибки `Close`, `Wait`, `Cancel` и других lifecycle operations;
- корректно ли освобождаются ресурсы при частичном успехе;
- не возникает ли panic на обычном пользовательском вводе;
- определены ли границы ответственности функций и типов;
- не зависит ли поведение от случайного порядка, timing или окружения;
- не создаёт ли код проблем с правами, путями, процессами, сигналами или cleanup.

Для concurrency-кода дополнительно проверяются ownership данных, завершение goroutines, cancellation и race conditions.

### 6. Проверить тесты

Для каждого важного observable behavior нужно проверить:

- есть ли тест успешного сценария;
- есть ли тесты ожидаемых ошибок;
- проверяется ли результат, а не только факт вызова функции;
- проверяются ли границы и частично выполненные операции;
- явно ли обозначены platform assumptions;
- детерминирован ли тест и имеет ли timeout;
- не дублирует ли тест внутреннюю реализацию.

Тест считается полезным, если после изменения реализации он способен обнаружить нарушение поведения, описанного в спецификации.

### 7. Проверить документацию и handoff

До завершения review должны быть синхронизированы:

- `proposal.md`, `design.md` и `tasks.md` текущей change;
- соответствующие ADR или архитектурные документы;
- `docs/session-context.md`;
- известные ограничения, отложенные вопросы и evidence проверок.

## Критерии качества кода

Готовый код должен:

- быть идиоматичным для Go и отформатированным `gofmt`;
- использовать короткие и точные имена пакетов, типов и функций;
- иметь простые функции с одной понятной ответственностью;
- возвращать ошибки явно и сохранять полезный контекст;
- документировать экспортируемый API и нетривиальные решения;
- использовать стандартную библиотеку, если дополнительная зависимость не оправдана;
- не скрывать важные lifecycle operations;
- не смешивать CLI parsing, domain decisions, platform operations и storage без архитектурного основания;
- оставаться понятным разработчику, который не участвовал в написании изменения.

Код не обязан быть идеальным или максимально обобщённым. Обязателен тот уровень качества, который сохраняет корректность, понятность и возможность развития архитектуры.

## Формат результата review

Итог review оформляется в следующем порядке:

1. **Решение:** `готово`, `нужны исправления` или `заблокировано проверкой`;
2. **Blocker/Major findings:** список с файлом, местом, последствием и предлагаемым направлением исправления;
3. **Minor/Nit findings:** необязательные улучшения;
4. **Acceptance criteria:** таблица с результатом проверки каждого критерия;
5. **Проверки:** команды и результаты;
6. **Архитектурные выводы:** что подтверждено и какие решения отложены;
7. **Документация:** какие документы обновлены;
8. **Следующий шаг:** следующая task, fix task или design change.

Если Blocker или Major findings отсутствуют, change можно считать готовой после обновления документов. Minor и Nit замечания не должны искусственно блокировать переход к следующему блоку.
