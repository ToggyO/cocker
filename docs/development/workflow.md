# Workflow

## Правило источника истины

Код реализует актуальную спецификацию. Если код и спецификация расходятся, расхождение нужно явно исправить: изменить код, изменить спецификацию или оформить архитектурное решение.

## Структура change

Каждая значимая возможность описывается отдельной change-директорией:

```text
docs/changes/<id>-<name>/
    proposal.md
    design.md
    tasks.md
```

`proposal.md` описывает цель и пользовательскую ценность.

`design.md` описывает устройство решения, границы ответственности, зависимости, ошибки и будущие точки расширения.

`tasks.md` содержит маленькие задачи, которые можно реализовать и проверить отдельно.

## Обязательные разделы implementation task

Каждая задача должна содержать:

- цель;
- связь со спецификацией;
- зачем это нужно системе;
- краткую справку по Linux или Go теме;
- словарь новых терминов и системных вызовов;
- предусловия;
- изменяемые компоненты;
- критерии приёмки;
- способ проверки;
- вопросы для code review;
- результат выполнения.

## Формат сопровождения при реализации

При работе над задачами код пишет разработчик проекта. По умолчанию рекомендации к следующему шагу должны быть компактными и содержать:

- сигнатуру функции или теста;
- цель и проверяемое поведение;
- необходимые imports или стартовые детали;
- ключевые assertions и ожидаемый результат;
- команды форматирования, тестирования и проверки.

Полный листинг реализации не приводится без отдельной просьбы. Это позволяет сохранять ручную практику написания Go-кода и оставляет code review содержательным.

Если задача сложная, сначала объясняются необходимые Go или Linux concepts, затем даётся минимальная точка старта. После реализации разработчик присылает код на review.

## Пошаговый рабочий цикл задачи

Работа над implementation task выполняется небольшими последовательными шагами:

1. Выбрать одну следующую задачу из `tasks.md`.
2. Объяснить, какую проблему решает задача и какое наблюдаемое поведение проверяется.
3. Дать краткую справку по необходимым Go или Linux concepts.
4. Указать сигнатуру, расположение файла, необходимые imports и стартовые детали.
5. Разработчик самостоятельно пишет код или тест.
6. Разработчик присылает изменённые файлы или фрагменты на review.
7. Выполнить code review: корректность, границы абстракций, обработка ошибок и соответствие specification.
8. Запустить форматирование, unit tests, `go vet` и необходимые integration checks.
9. Исправить найденные проблемы и повторить проверки.
10. Зафиксировать результат задачи и только после этого переходить к следующей.

После завершения всех задач блока обязательно выполняется отдельное финальное feature review по [`feature-review.md`](feature-review.md). Переход к следующему блоку запрещён до фиксации результата этого review.

На одном шаге не перепрыгиваем через незавершённую задачу и не добавляем следующий слой архитектуры без необходимости текущей task.

## Большое ревью после блока задач

После завершения связанного блока задач выполняется отдельное milestone review. Блоком считается набор задач, который реализует один законченный архитектурный слой или change.

Это обязательный этап workflow, а не дополнительная проверка по желанию. Его нельзя заменить успешным выполнением unit tests, `go vet` или review отдельных задач.

Границы блока определяет сопровождающий агент на этапе планирования. До начала реализации агент явно сообщает:

- название блока;
- его цель;
- входящие задачи;
- критерий завершения;
- что сознательно не входит в блок;
- какие документы и проверки должны быть обновлены.

Агент отвечает за то, чтобы блок имел законченный технический результат и не был искусственно разделён так, чтобы отложить обязательное архитектурное ревью. Если в ходе реализации границы меняются, изменение фиксируется до перехода к следующей задаче.

Большое ревью включает:

- выполнение порядка и критериев из [`feature-review.md`](feature-review.md);
- проверку всех acceptance criteria блока;
- сверку фактической структуры кода со спецификациями и ADR;
- проверку направления зависимостей и границ абстракций;
- поиск дублирования, временных решений и неявных platform assumptions;
- проверку обработки ошибок, cleanup и lifecycle transitions;
- повторный запуск unit, static и соответствующих integration checks;
- review тестового покрытия по наблюдаемому поведению;
- обновление architecture documents, change status и `docs/session-context.md`;
- фиксацию отложенных вопросов и решений для следующего блока.

Следующий блок не начинается, пока результаты milestone review не зафиксированы в репозитории. Если review выявляет архитектурную проблему, сначала создаётся отдельная fix task или design change.

Для тестов дополнительно описываются:

- что именно проверяет тест;
- почему выбран этот сценарий;
- какие assertions обязательны;
- какие platform assumptions используются;
- какой результат считается успешным.

## Учебная справка

Справка объясняет необходимый минимум перед реализацией. Она не заменяет полноценное изучение темы, но должна отвечать на вопросы:

- какую проблему решает механизм;
- где он находится: CLI, Go runtime, kernel, filesystem или userspace;
- какие данные и ресурсы он создаёт;
- какие права нужны;
- что произойдёт при ошибке;
- как проверить результат руками и тестом.

Для системных вызовов также указываются их Linux-ограничения и используемый пакет `golang.org/x/sys/unix`.

## Передача работы между сессиями

После каждой завершённой задачи обновляются:

- `docs/session-context.md`;
- статус задачи в `tasks.md`;
- список известных решений в `docs/adr/`;
- команды проверки и их результат.

Новая сессия должна начать с чтения `README.md`, `docs/session-context.md`, активного `tasks.md` и связанных спецификаций.
