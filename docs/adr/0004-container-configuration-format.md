# ADR-0004: JSON-файл и CLI-флаги для конфигурации контейнера

## Статус

Accepted for MVP

## Контекст

Команде `run` нужно передавать параметры контейнера:

- rootfs;
- command и arguments;
- environment variables;
- working directory;
- hostname;
- resource limits;
- mounts;
- stdio policy;
- будущие network и security settings.

Пользователю нужен короткий способ запустить команду вручную и отдельный формат для повторяемых, читаемых и проверяемых конфигураций.

## Краткая справка: configuration versus domain model

Конфигурационный файл — внешний формат данных. Он описывает, что пользователь хочет получить.

`ContainerSpec` — внутренняя модель, с которой работают application и runtime layers.

Эти понятия нельзя полностью смешивать: внешний формат может измениться, а domain model должна оставаться стабильной. Между ними нужен parse/validate/normalize шаг.

## Краткая справка: JSON в Go

Стандартный пакет `encoding/json` умеет преобразовывать JSON в Go structs и обратно. Он не выполняет полную предметную валидацию автоматически.

Например, JSON может синтаксически корректно содержать отрицательный лимит памяти. Поэтому после decoding нужны отдельные validation rules.

Неизвестные поля по умолчанию могут игнорироваться. Для пользовательской конфигурации это опасно: опечатка способна незаметно отключить ожидаемую настройку. При чтении configuration file нужно рассмотреть строгий decoder.

## Решение

Для MVP поддерживаем:

1. CLI-флаги для основных параметров команды `run`.
2. JSON-конфигурацию через `--config <path>`.
3. Единую внутреннюю модель `ContainerSpec`.

CLI-флаги и JSON не являются двумя разными runtime paths. Они преобразуются в одну нормализованную модель до начала создания контейнера.

## Пример CLI

```text
cocker run \
  --rootfs ./rootfs \
  --memory 256M \
  --pids 64 \
  --env APP_ENV=dev \
  /bin/sh
```

## Пример JSON

```json
{
  "rootfs": "./rootfs",
  "command": ["/bin/sh"],
  "hostname": "cocker-dev",
  "env": {
    "APP_ENV": "dev"
  },
  "resources": {
    "memory": "256M",
    "pids": 64
  }
}
```

Точная JSON schema будет описана отдельной спецификацией перед реализацией.

## Правила приоритетов

Если параметр задан и через JSON, и через CLI, явный CLI-флаг имеет приоритет.

Командные аргументы после `--` или после обязательной части синтаксиса `run` должны однозначно отделяться от опций самого `cocker`.

Неоднозначные или конфликтующие значения должны приводить к ошибке до создания процесса и системных ресурсов.

## Нормализация и валидация

Configuration pipeline:

```text
CLI / JSON
    │
    ▼
Decode
    │
    ▼
Merge explicit overrides
    │
    ▼
Normalize defaults
    │
    ▼
Validate ContainerSpec
    │
    ▼
Application layer
```

Примеры validation rules:

- rootfs должен быть указан и существовать;
- command не может быть пустой;
- memory limit должен иметь допустимый формат и не быть отрицательным;
- pids limit должен быть положительным;
- environment variable должна иметь корректное имя;
- рабочая директория должна быть совместима с rootfs;
- несовместимые параметры должны быть отклонены до запуска.

## Причины выбора

### Стандартная библиотека

JSON поддерживается `encoding/json`, поэтому MVP не получает обязательную зависимость от YAML/TOML parser.

### Разделение ручного и повторяемого сценария

Флаги удобны для первой проверки и интерактивной работы. JSON подходит для воспроизводимых запусков, integration tests и будущего API.

### Расширяемость

В будущем daemon или HTTP/Unix socket API сможет принимать ту же нормализованную модель или совместимую schema, не заставляя CLI быть единственным источником конфигурации.

## Последствия

### Положительные

- быстрый ручной запуск;
- воспроизводимые конфигурации;
- отсутствие YAML/TOML-зависимости в MVP;
- единая валидация для CLI и файла;
- удобная подготовка к API.

### Отрицательные

- нужно поддерживать merge и приоритеты двух источников;
- JSON менее удобен для комментариев, чем некоторые альтернативы;
- расширение schema требует аккуратной обратной совместимости;
- отдельные пользовательские типы вроде `256M` потребуют собственного parser.

## Альтернативы

### Только CLI-флаги

Отклонено: конфигурации становятся длинными и плохо воспроизводимыми при добавлении mounts, security и networking.

### Только JSON

Отклонено: простой запуск команды требует создания отдельного файла.

### YAML

Отклонено для MVP: стандартная библиотека Go не содержит YAML parser, а добавление зависимости не даёт существенной выгоды на раннем этапе.

### TOML

Отклонено по той же причине. TOML можно рассмотреть после MVP, если реальные конфигурации станут слишком неудобными в JSON.

### Dockerfile или OCI config как первый формат

Отклонено: это потребовало бы преждевременно поддерживать отдельную спецификацию образов и build process.

## Требования к реализации

Configuration package должен:

1. Разделять decoding, validation и normalization.
2. Не создавать namespaces, cgroups или процессы.
3. Возвращать ошибки с указанием поля и причины.
4. Отвергать неизвестные JSON-поля после выбора strict policy.
5. Иметь unit tests для валидных, невалидных и конфликтующих конфигураций.
6. Преобразовывать memory и CPU values во внутренние типы до application layer.
7. Не позволять CLI-команде обходить обязательную validation.
