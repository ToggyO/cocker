# ADR-0001: Использовать cgroup v2

## Статус

Accepted for MVP

## Контекст

`cgroups`, или control groups, — механизм Linux kernel для группировки процессов и управления их ресурсами.

С помощью cgroups можно:

- ограничивать потребление памяти;
- ограничивать или учитывать CPU;
- ограничивать количество процессов;
- наблюдать фактическое потребление ресурсов;
- применять политики к группе процессов вместо настройки каждого процесса отдельно.

Контейнер в `cocker` будет не только изолирован через namespaces, но и ограничен по ресурсам. Поэтому runtime должен уметь создавать cgroup, помещать в неё процесс, записывать лимиты и удалять группу после завершения контейнера.

В Linux существуют две основные модели: cgroup v1 и cgroup v2.

### Краткая справка: cgroup v1

В v1 разные контроллеры обычно организованы в отдельных hierarchies. Например, memory и CPU могут находиться в разных деревьях каталогов. Это историческая модель с большим количеством вариантов конфигурации и совместимости.

### Краткая справка: cgroup v2

В v2 используется unified hierarchy: контроллеры работают в едином дереве cgroups. Настройка выполняется через файлы интерфейса в одной иерархии, например `memory.max`, `cpu.max` и `pids.max`.

Эти файлы находятся в cgroup filesystem, обычно смонтированной в `/sys/fs/cgroup`. Запись значения в такой файл является способом передачи настройки kernel через filesystem interface.

## Решение

Для MVP поддерживаем только cgroup v2.

Первая реализация будет работать с локальной unified hierarchy и использовать Linux filesystem interface. Доступ к системным вызовам, если он потребуется, будет изолирован в `internal/platform/linux/cgroup`, а операции с файлами cgroup будут отделены от domain model.

## Причины выбора

### Меньше вариантов поведения

Поддержка двух версий с самого начала добавила бы обнаружение версии, разные пути настройки, разные форматы файлов и дополнительные integration tests. Для учебного и ограниченного MVP это увеличивает объём кода без улучшения основного сценария.

### Более цельная модель

Unified hierarchy лучше соответствует модели контейнера как одной группы процессов, для которой одновременно задаются memory, CPU и pids limits.

### Актуальная целевая модель Linux

Проект ориентирован на современные Ubuntu-системы. Проверка конкретных минимальных версий Ubuntu и kernel будет вынесена в отдельное compatibility document.

### Удобная связь с учебными целями

Одна реализация позволит подробно разобрать:

- иерархию процессов;
- controller delegation;
- интерфейс kernel через псевдофайлы;
- различие между настройкой лимита и наблюдением usage;
- ошибки прав доступа и отсутствующих controllers.

## Последствия

### Положительные

- проще domain model ресурсов;
- меньше platform-specific ветвлений;
- единый набор integration tests;
- проще объяснить lifecycle cgroup;
- легче добавлять memory, CPU и pids limits последовательно.

### Отрицательные

- `cocker` не будет работать на системах, где доступна только cgroup v1;
- пользователю нужна корректно настроенная cgroup v2 hierarchy;
- создание и настройка cgroup могут требовать root или специально делегированных прав;
- compatibility с legacy Linux откладывается.

## Границы решения

Это решение не определяет:

- запуск rootless контейнеров;
- способ делегирования cgroup subtree;
- точный каталог хранения cgroups;
- набор контроллеров за пределами memory, CPU и pids;
- политику поведения при недоступном контроллере.

Эти вопросы будут решены при проектировании runtime и security model.

## Требования к реализации

Реализация cgroup должна:

1. Проверять наличие cgroup v2.
2. Проверять доступность требуемых controllers.
3. Создавать отдельную cgroup для контейнера.
4. Записывать resource limits до запуска или до помещения процесса в группу согласно выбранной модели запуска.
5. Добавлять PID процесса в cgroup.
6. Читать usage и состояние при необходимости.
7. Удалять cgroup после завершения процесса.
8. Возвращать ошибку с названием операции и системным путём.
9. Безопасно обрабатывать повторный cleanup.

## Проверка решения

До реализации runtime нужно проверить на целевой Ubuntu-системе:

```text
stat -fc %T /sys/fs/cgroup
cat /sys/fs/cgroup/cgroup.controllers
```

Ожидается filesystem type `cgroup2fs` и наличие нужных controllers. Конкретные команды диагностики и integration test будут описаны в отдельной change specification.

## Альтернативы

### Поддерживать cgroup v1 и v2 сразу

Отклонено для MVP из-за увеличения количества platform branches, тестов и вариантов ошибок.

### Сначала не добавлять resource limits

Отклонено, поскольку управление ресурсами является частью целевого поведения container runtime и важно для понимания отличия изоляции от ограничения ресурсов.

### Использовать готовую библиотеку container runtime

Отклонено в рамках учебных целей и требования разобраться с Linux kernel interfaces самостоятельно.
