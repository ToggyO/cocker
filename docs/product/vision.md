# Cocker: Product Vision

## Статус документа

- Статус: draft
- Версия: 0.1
- Последнее обновление: 2026-10-11

## Назначение

`cocker` — Linux-only инструмент командной строки для запуска процессов в изолированном и ограниченном окружении.

Проект создаётся как рабочий container runtime с production-oriented архитектурой и одновременно как практический путь восстановления знаний Go, Linux и системного программирования.

Основной пользователь взаимодействует с системой через CLI. Позже тот же runtime должен быть доступен через локальный daemon и API.

## Проблема

Запуск процесса напрямую на хосте даёт ему доступ к общему пространству процессов, файловой системе, hostname, IPC и ресурсам машины. Для безопасной и предсказуемой работы нужно уметь запускать процесс с отдельным окружением и контролировать его потребление ресурсов.

Docker решает эту задачу как большая экосистема. `cocker` реализует ограниченное ядро этой идеи, чтобы сделать устройство container runtime понятным через собственную реализацию и наблюдаемое поведение.

## Цели MVP

MVP должен позволять:

1. Запустить команду внутри локального root filesystem.
2. Изолировать процесс с помощью Linux namespaces.
3. Ограничить его основные ресурсы через cgroup v2.
4. Передать процессу стандартные потоки ввода и вывода.
5. Корректно обработать сигналы, завершение и exit code.
6. Просмотреть список и состояние созданных контейнеров.
7. Остановить работающий контейнер.
8. Удалить временные системные ресурсы после завершения.
9. Сохранить метаданные, достаточные для диагностики и управления жизненным циклом.

## Цели после MVP

Архитектура должна позволять добавить:

- импорт и хранение образов;
- filesystem layers и overlayfs;
- volumes;
- сетевые namespaces, bridge, veth и port mapping;
- user namespaces и rootless mode;
- Linux capabilities и seccomp;
- daemon и Unix socket API;
- параллельное управление контейнерами;
- restart policy и health checks;
- мониторинг ресурсов и события;
- OCI-совместимые форматы и интеграцию с существующими инструментами.

## Не входит в MVP

В MVP не входят полноценная совместимость с Docker CLI, загрузка образов из Docker Registry, собственный registry, распределённый режим, поддержка Windows и macOS kernel APIs, оркестрация контейнеров и полная OCI runtime specification.

На macOS проект можно редактировать, но runtime MVP запускается внутри Linux-среды, например Ubuntu VM.

## Пользовательский сценарий MVP

Пользователь подготавливает rootfs и запускает команду:

```text
cocker run --rootfs ./rootfs --memory 256M --pids 64 /bin/sh
```

`cocker` создаёт контейнер, настраивает изоляцию и ограничения, запускает `/bin/sh`, подключает стандартные потоки и ждёт завершения процесса.

Пользователь может посмотреть состояние:

```text
cocker list
cocker inspect <container-id>
```

Для работающего контейнера доступна остановка:

```text
cocker stop <container-id>
```

После завершения процесс не должен оставлять неконтролируемые cgroups, mount points или записи runtime state.

## Принципы продукта

### Наблюдаемое поведение важнее внутренней реализации

Команды, состояния, ошибки, exit codes и результаты изоляции определяются спецификациями. Внутреннюю реализацию можно менять, если сохраняется согласованное поведение.

### Явные ограничения платформы

Система не скрывает необходимость Linux kernel features. При отсутствии namespace, cgroup или требуемого права пользователь получает понятную ошибку с указанием причины.

### Минимум магии

Основные системные механизмы реализуются через стандартную библиотеку Go и `golang.org/x/sys/unix`. Высокоуровневые фреймворки и готовые container runtime библиотеки не являются частью базовой реализации.

### Безопасное расширение

Операции с ядром, filesystem, storage и networking должны иметь отдельные границы. Это позволит развивать runtime без переноса Linux-specific деталей в CLI и domain model.

### Диагностируемость

Каждый отказ запуска должен объяснять, на каком шаге он произошёл и какой системный ресурс оказался недоступен. Состояние контейнера и результаты завершения должны сохраняться достаточно долго для анализа.

## Критерии успеха MVP

MVP считается успешным, если на поддерживаемой Ubuntu-системе:

- команда запускается в отдельном PID namespace;
- процесс получает отдельное mount namespace и заданный rootfs;
- ограничения памяти, CPU и числа процессов применяются через cgroup v2;
- `list`, `inspect` и `stop` согласованно отражают состояние контейнера;
- SIGTERM и SIGKILL обрабатываются предсказуемо;
- exit code процесса доступен пользователю;
- после нормального и аварийного завершения выполняется cleanup;
- ключевые сценарии покрыты unit- и Linux integration tests;
- документация позволяет новому разработчику собрать, запустить и проверить проект.

## Ограничения разработки

- Целевая ОС: Linux.
- Первичная локальная среда: Ubuntu.
- Код пишет разработчик проекта вручную.
- Работа ведётся через спецификации и небольшие проверяемые задачи.
- Каждая системная задача сопровождается краткой учебной справкой о соответствующем механизме Linux и API Go.
- Все решения, текущий прогресс и команды проверки фиксируются в репозитории.

## Открытые вопросы

Эти вопросы не блокируют написание vision, но должны быть решены в архитектурных документах:

- какая минимальная версия Go поддерживается;
- поддерживаем ли только cgroup v2;
- будет ли rootless mode обязательной целью после MVP;
- какой формат rootfs и конфигурации используется первым;
- где по умолчанию хранится runtime state;
- требуется ли запуск контейнера от имени root для первой версии.
